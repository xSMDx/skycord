# End-to-End Encryption — Design

**Status:** designed, NOT built. Parked deliberately.
**Build order:** mobile app → channels → **this**.
**Date:** 2026-08-09

---

## Why this exists

Skycord has no encryption of any kind today. Messages sit in Mongo as plaintext
`String`, and the server reads them in 19 places. LiveKit runs as an SFU with no
`e2ee` option configured, so it decrypts and re-encrypts every call stream.

There is already a **false claim shipping**: `VoiceConnectedPanel.vue:54` renders
"LiveKit · end-to-end media". `callMenu.ts:16` carries a comment reading
"View Verification Code — no E2EE", so the gap was known and the string was
never corrected. **Fix that string before any public Terms page claims
anything about encryption.**

The decision was: build it first, then claim it.

---

## The model in one paragraph

Encryption is **opt-in per conversation**, chosen with a checkbox at creation,
and **permanent** once chosen. Each user has one identity keypair; each
encrypted conversation has one symmetric key, wrapped separately for every
member, rotated whenever membership changes. A new device is authorised by
**six-number verification against an already-logged-in device**, with a
**single per-user backup code** as break-glass. The server stores only
ciphertext and public keys, and can decrypt nothing.

---

## Decisions, and why

### Opt-in per conversation, not global

Unencrypted conversations keep server-side search, link embeds, notification
previews and `@everyone` detection. Encrypted ones trade those away. Making it
global would impose that cost everywhere and, more importantly, would make
moderation impossible for community servers — a real problem for self-hosters.

**Encryption is one-way.** A conversation can never be un-encrypted. If it
could, whoever could flip that switch could silently downgrade a room and start
reading. Element does the same, for the same reason.

### Key hierarchy

```
Backup code  (one per user, shown once, never sent to the server)
      │  PBKDF2 → wrapping key
      ▼
Identity keypair  (ECDH P-256, one per user)
      │  private half wrapped by the above → "key bundle", stored server-side as ciphertext
      │  public half uploaded in the clear
      ▼
Conversation key  (AES-GCM 256, one per conversation)
      │  wrapped per member via ECDH(my private, their public)
      ▼
Message  (AES-GCM, fresh IV per message)
```

The server gains three new pieces of data, all opaque to it: each user's public
key, each user's wrapped key bundle, and per conversation a set of
`{ memberId, wrappedConversationKey }`.

**ECDH P-256, not X25519.** X25519 is the better curve but WebCrypto support is
recent and uneven, and the web client rules it out today. Revisit if Skycord
ever goes Chromium-only.

**PBKDF2, not Argon2id.** Argon2id is correct for *password*-derived keys and
resists GPU cracking far better, but needs a WASM dependency. The backup code is
a generated high-entropy value, not a human-chosen password, so brute force is
infeasible either way. **This reasoning only holds because the input is
generated — if anything is ever wrapped with a user-chosen password, switch to
Argon2id.**

No crypto library. WebCrypto primitives only.

### Per-conversation key, rotated on membership change

One symmetric key per conversation, re-wrapped for each member. Rotated when
anyone joins or leaves, so a new member cannot read history and a removed member
cannot read anything after.

**Accepted weakness: no forward secrecy.** Compromising a key exposes everything
that key could read. A ratchet (libsignal/MLS) would fix this but costs a heavy
dependency, device-to-device session state, out-of-order and multi-device
delivery handling, and a large surface for silent bugs. Rejected as
disproportionate for now — this is roughly what Element shipped first.

### Lazy enrolment

Keys are generated the first time a user ticks the encrypt box or is invited to
an encrypted conversation — not at registration. Users who never touch E2EE are
never shown a "save this or lose everything" screen, and those who do see it at
the moment it makes sense.

### Device verification — the six numbers

New device authorisation is a **transfer scheme**, modelled on Bluetooth Passkey
Entry:

- The already-logged-in device displays **six values from 0–21** (22 possible
  values per position, duplicates allowed)
- The user enters them on the new device
- **22⁶ = 113,379,904 combinations** (~26.8 bits) — comfortably above Bluetooth's
  6-digit 10⁶

> **The single most important requirement in this document:** the six numbers
> MUST be derived from the two devices' **ECDH shared secret**. Not generated by
> the server. Not picked randomly by one device and transmitted. If the server
> invents the code, the server can man-in-the-middle both sides and read
> everything, and the verification becomes theatre. Derived from the shared
> secret, a MITM computes different numbers on each side and verification fails.
> That is the entire security property.

Rejected along the way: an *ordering* game over 6 items (6! = 720 ≈ 1-in-720 for
an attacker — far too weak) and pure emoji-style comparison (fine, but the user
preferred entry, and 26.8 bits of transfer is sufficient).

### Lockout policy

- 5 failed verification attempts → escalating backoff: 1 min, 5, 30, 1 hr
- Tracked **per attempting device**, not per account — otherwise anyone with the
  password can lock the owner out by failing five times
- Blocks **verification only**. Never login, never unencrypted chats, never calls
- **The backup code always bypasses the backoff.** The lockout exists to stop
  someone guessing six numbers; the backup code has far more entropy, so gating
  it punishes only the legitimate owner

Rejected: a month-long login ban. It was a denial of service against the account
owner and a griefing vector.

### Backup code: one per user

Covers the identity key, and therefore every encrypted conversation including
future ones. Per-chat codes were rejected — a user in 15 encrypted chats managing
15 codes will save none of them.

### Runtime key storage

The unwrapped identity private key lives in **IndexedDB as a non-extractable
`CryptoKey`**. Script can use it to decrypt; the raw bytes cannot be exported.
Injected script could still decrypt while the page is open, but cannot steal the
key and leave with the user's whole history.

This matters concretely: a stored XSS was found and fixed in this codebase on
2026-08-09. Assume there will be another.

### Login

Password plus an emailed code on a **new device or unrecognised location** —
not on every login. Every-login was rejected as heavy, and because it makes
email a single point of failure (password reset already goes there, so the
"second factor" becomes the same factor twice).

Instances with no email configured degrade to password-only. Self-hosters are
not blocked; their instance is simply weaker, and that should be visible.

## Consequences to design around

### The pending-key problem

Someone invited to an encrypted conversation before they have keys can't be sent
the conversation key — there's no public key to wrap it for. The server marks
them `pendingKey` and prompts enrolment at next login; once their public key
exists, the first online member re-wraps for them.

**Unavoidable consequence: a user cannot enter an encrypted conversation until
another member is online.** The server physically cannot do it. In a DM this
resolves in seconds; in a quiet group it could take hours. The UI must say
"waiting for a member to share the key" — not spin silently.

### What breaks in encrypted conversations

| Feature | Encrypted behaviour |
|---|---|
| Server-side search | **Gone.** Client-side only, over what that device has downloaded. Affects roadmap #49 (search with tags). |
| Link embeds | **Gone**, or client-fetched — which leaks the reader's IP to the linked site. Affects roadmap #48. |
| Push notification previews | Sender name only, never content. Relevant once mobile/Electron ship. |
| `@everyone` | Needs a sender-set boolean beside the ciphertext. Server learns *that* a message mentions everyone, not the text. Accepted metadata leak. |

### What still works

Sidebar last-message preview, reply previews, editing, deleting, reactions,
pinning — all of it, because the client holds the keys and decrypts locally.
These are commonly assumed lost; they aren't.

### Server code that must change

19 reads of `msg.content` across `chatSocket.ts`,
`messagesController.ts` and `conversationsController.ts` — reply previews,
`@everyone` regexes, edit propagation, and the `lastMessage` field in
`getMyDMs`. Each needs a path that skips or defers to the client when a
conversation is encrypted.

All client sends funnel through `useSocket.ts`, which is a single clean
chokepoint to encrypt at.

### No migration needed

Because encryption is opt-in per **new** conversation, everything that exists
stays unencrypted and keeps working. The offer to delete old messages and logs
was made when this looked like it might be mandatory — it isn't, and nothing has
to be wiped.

## LiveKit media

LiveKit supports E2EE natively via insertable streams. Today the room is created
as `new Room({ adaptiveStream: true, dynacast: true })` — no `e2ee` key.

Enabling it needs a key provider and a worker, with the room key distributed
through the same per-conversation mechanism above. Largely independent of the
messaging work and much smaller; it can ship separately.

Note: E2EE interacts with `dynacast` and server-side features, and rules out any
future server-side recording or transcription.

- Key bundle re-wrap flow on backup-code regeneration
- Whether reactions are encrypted or left plaintext
