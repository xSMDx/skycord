# v0.22.0 — release plan

Planned 2026-11-09 at the owner's go-ahead ("Yes, plan v0.22.0"). v0.21.0 is live everywhere: the
server and web client, the Windows app and the Android app (beta). v0.22.0 is the next minor release
because it adds features: chat attachments and a Linux desktop app.

Nothing in this plan merges, tags or deploys without the owner's yes at that step.

## What goes in

| PR | What | Release it rides |
|---|---|---|
| #17 | Chat attachments, with previews for uploads and GIFs | server and web `v0.22.0` |
| #18 | Android: save attachments to Downloads, files-only notices | `android-v0.22.0` (needs #17) |
| #14 | Desktop app for Linux (AppImage + .deb), released beside Windows | `desktop-v0.22.0` |
| #16 | Bundled LiveKit v1.9.0 → v1.13.11 (no more re-join every 15 s) | server `v0.22.0` (self-host files) |

| #10 | Landing: the main download follows the visitor's system | landing deploy |
| #15 | Landing: Linux visitors get Download for Linux | landing deploy, after `desktop-v0.22.0` publishes |

Merge any time, no release needed: #11 (roadmap row 6b), #12 (dev app id), #13 (e2e device log).

## Before merging

1. **#17's catch-up gap.** `GET /users/me/missed` does not send `attachments` yet, so a files-only
   message the phone catches up on after being offline is still notified as "New message" (#18
   already reads the field). Add `attachments` to the catch-up payload on `chat-attachments`,
   with a test, before #17 merges.
2. **#18 on a phone.** Download on a file card and in the large view, and that the "done"
   notification opens the file. Owner, on a real phone, with the debug APK from #18's branch, or
   on the emulator, headless.

## Merge order

1. #11, #12, #13 (independent).
2. #16.
3. #17, then #18 (#18 depends on #17's payloads).
4. #14.

## Release (owner says yes at each step)

1. Tag `v0.22.0` on the release-prep merge commit. The release workflow builds the images (`skycord`,
   `skycord-music`) and rehearses install, update and rollback.
2. **Deploy production** (the pm2 host, `srv9617840187`), owner pasting in MobaXterm:
   - pull, then confirm `git log --oneline -1` shows the release-prep merge;
   - `npm install --include=dev && npm run build && rsync` of `dist/` (the app);
   - add `CLAMD_HOST=10.250.250.20` and `CLAMD_PORT=3310` to `~/sykord/.env` (the existing
     `skycord-clamav` container on the `skycord-music` network), then
     `pm2 restart sykord-api --update-env`. **The server changed in this release**, unlike v0.21;
   - check production's own LiveKit:
     `docker exec livekit-server /livekit-server --version`. Below 1.9.1 it re-joins calls every
     15 s and should be updated;
   - `node scripts/smoke.mjs`, then upload a photo and a file as a non-owner in a real channel and
     check the scan ran (an EICAR test file must be refused).
3. Tag `desktop-v0.22.0`. This is the first run of #14's draft → windows + linux → publish
   workflow. Check that the release holds `Skycord-Setup-0.22.0.exe`, `latest.yml`,
   `Skycord-0.22.0.AppImage`, the `.deb` and `latest-linux.yml`, and that the installed Windows
   app offers the update.
4. Tag `android-v0.22.0` (versionCode 2200). Check `latest.json` says 0.22.0. **This is the first
   real test of the Android self-update**: a phone on the 0.21.0 beta must offer 0.22.0.
5. Merge #15 (Linux download), then deploy the landing: pull, `cp -r landing/*`,
   `stamp-assets.mjs`, and check `content.js` names v0.22.0.

## After

- Smoke check, and the owner's checks: attachments on a phone, the Android update, the Windows
  update, and the Linux download on a Linux machine if one is to hand.
- Self-hosters: the release notes say to set `CLAMD_HOST` (or keep the scanner compose file) for
  scanned uploads, and that their own LiveKit needs 1.9.1 or newer.
